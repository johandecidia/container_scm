Two things this element must keep doing: * It carries `data-scm-map-source`, the GeoJSON URL describing the current selection. The map itself is deliberately not in here. * It is `display: contents` (Tailwind `contents`), so the blocks below are items of the page's grid rather than children of this element. {% comment %} 1. Status. Every card is an action. Tracking leads, and since TRACK-UX it is the card the board's own default state corresponds to: what the platform is actively watching is the first thing an operator wants to know, and it counts distinct containers under a live watch — see VisibilityOverview.tracking_container_count, which is where "one box, two sources, one tracked container" is decided. Tracking, Delayed and Exceptions switch this board's view; the arrival cards still drill into the Arrivals queue, and Active shipments into the shipments list. That is a change from UX-3, where the operational three all left for a queue: the three now have a view here to switch to, and the queues are still one click away from the section headers below. Since LOC-3 the two arrival cards are the arrival lifecycle's own numbers rather than an ETA comparison of their own. "Arriving ≤7d" counts what is still outstanding, so a shipment gated in on Monday stops being counted as Wednesday's work; "Awaiting receipt" is the gap between a box landing and somebody taking it into their records. {% endcomment %}

{% comment %} 2. The view, then the filters. Local to this board: they narrow what is shown, they do not search the platform. `hx-push-url` keeps the state in the address bar so a selection can be linked and bookmarked. The view is a one-of choice and renders as one: three buttons, exactly one selected, in the same form as the filters — so a filter change keeps the view and a view change keeps the filters. The counts are the read model's, taken before this board narrowed anything, so Exceptions still reads 3 while Tracking is on screen. That is the number that makes the button worth pressing. {% endcomment %}
{% comment %} Radios rather than buttons, and the reason is the form. A submit button and a hidden input would both be named `view` and both be sent, leaving which one won to parameter order; one checked radio out of three sends exactly one value, and it survives a change to any other control on this row. The input is `sr-only` rather than `hidden` so the group stays keyboard- and screen-reader-operable; the label around it is what carries the styling and the count. {% endcomment %}
